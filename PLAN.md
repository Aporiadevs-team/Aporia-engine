# Aporia Engine

## Текущий статус (2026-11-21)

| Ветка | Версия | Состояние |
| --- | --- | --- |
| `main` | 1.0.0 (`v1.0.0`) | Релизная линия: движок + `create_project.bat`, чистое дерево. |
| `experimental/dev` | 0.1.0 | Линия разработки: та же база + рефакторинг `ShaderManager` и `Support/Log`; инициализатора проекта нет. |

Рабочая копия dev опережает запушенную ветку `experimental/dev` на один
локальный рефакторинг, который ещё не закоммичен.

Реализовано:

- **Ядро**: `Game` / `Scene` / `Body`, runtime-реестр компонентов, fixed
  timestep 300 Гц с accumulator, `syncTransforms`, `destroyBody`.
- **Физика**: sphere/box/capsule и heightfield-террейн; SAT-манифолды (до 4
  контактов), sequential impulse (8 итераций), трение и восстановление,
  `raycast` / `raycastAll`, `lastContact(s)`, uniform spatial-hash broadphase,
  sleeping, предиктор руля (`SteeringConfig`).
- **Графика (Vulkan)**: headless и Win32 swapchain, HDR + ACES, PCF/PCSS-тени,
  планарные отражения, SMAA/TAA, LOD, TTF/MSDF-текст, SDF-прямоугольники и blur,
  небо и время суток, направленные/точечные/прожекторные источники, прозрачный
  проход для стекла и декалей.
- **Экспериментальное (`APORIA_EXPERIMENTAL`)**: многослойные материалы,
  многопоточная запись кадра (JobSystem + per-pass command buffers), UI-слои,
  froxel volumetric fog.
- **Погода (`APORIA_SEASONS`)**: сезоны (spring/summer/autumn/winter), осадки,
  аналитический туман, ветер.
- **Камера**: `CameraEffects` (bobbing, seat push, speed shake), `FreeFly`.
- **Сборка**: модульные CMake-опции, install rules + `find_package(AporiaEngine)`,
  CTest-раннеры и оконные render-тесты.

Ещё нет:

- ассет-кеша и импорта моделей (OBJ и т.п.);
- PBR-материалов (сейчас diffuse-слои);
- высокоуровневого UI (Main/Pause Menu, HUD);
- слоёв/масок коллизий и CCD в физике;
- debug-визуализации коллайдеров/сил и GPU-профилирования;
- аудио, скриптов, сети, softbody, skeletal-анимации;
- сериализации сцены;
- платформ кроме Windows.

## Видение

Aporia Engine — модульный C++ игровой движок, подключаемый к игре как код. Это
не редактор и не визуальный конструктор: игра сама создаёт сцену через публичный
API, а движок выполняет симуляцию и предоставляет графический слой.

Первый приоритет — Windows x64, C++20 и headless CLI-тесты. Основной графический
путь — Vulkan; окно, SDL3/GLFW и цикл приложения принадлежат внешнему проекту.
Внутри Aporia нет обязательного деления на «2D» и «3D»: сцена — это данные и
симуляция, а backend можно подключить или отключить независимо.

## Главный критерий — скорость создания базы

Ценность движка — время от пустого проекта до работающей базы: окно юзера
открыто, мир из мешей собран, Тело двигается вводом. Возможности оцениваются по
вкладу в эту скорость, а не по количеству функций.

- Юзер сам создаёт окно на любом API и сам держит цикл; движок получает контекст
  окна и никогда не создаёт окно сам.
- Сцена собирается через API; «мир» — это меши внутри сцены.
- Центральная абстракция — Тело: трансформ + опциональная физика + опциональный
  меш. Персонаж, машина и снаряд — это Тело плюс код игры, готовых сущностей в
  движке нет.
- Движок управляет input, render и закулисьем (время, физика, кеш ресурсов,
  память); правила игры пишет юзер.
- Ассеты «просто работают»: пачку файлов скушивает кеш, выдача по имени.
- Счётчик успеха этапа — строки хост-кода и минуты до работающей базы.

## Принципы разработки

- Сначала вертикальная среза, затем расширение подсистем.
- Минимальные зависимости между модулями; границы задаются интерфейсами.
- Каждая возможность включается отдельной CMake-опцией.
- Минимальная сборка `core + tests` не зависит от рендера, Vulkan, аудио и сети.
- Физический runtime работает без окна и графического драйвера.
- Aporia не владеет окном и не выбирает SDL3/GLFW.
- Платформенный код изолирован от игровой логики.
- Любая крупная подсистема проектируется вокруг тестируемого ядра.
- Не добавлять функциональность без измеримой цели этапа.
- Сохранять совместимость форматов ресурсов и версий сцен.
- Решения, которые трудно откатить, фиксировать в плане и ADR.

## Зафиксированные решения

- Язык runtime и тестов: C++20. Первая платформа: Windows x64.
- Публичный namespace: `Aporia`; внутренний: `apr`.
- Компоненты сцены: runtime-типы с регистрацией по type id.
- Окно и SDL3/GLFW принадлежат внешнему проекту; Aporia получает native/window/
  surface context.
- Редактор не планируется. Подключение игры — `add_subdirectory` в CMake.
- Публичная модель: `Game`, владеющий renderer-фасадом; сцена через
  `game.scene()`.
- Создание объекта возвращает стабильный handle; иерархия parent/child
  откладывается.
- Внутри Aporia нет обязательного деления на 2D и 3D.
- Физика: собственная реализация без готового physics engine; SI-единицы,
  Z-up, преобразование в Vulkan на границе graphics API.
- Solver: sequential impulses; `step()` использует 300 Гц, `step(frameDelta)` —
  accumulator с нужным числом fixed substeps.
- Инициализация renderer выполняется явно через `initGraphics(context)` после
  создания окна хостом.
- Библиотека собирается как shared DLL `AporiaEngine.dll` и копируется рядом с
  EXE host-проекта.
- Транспорт/машины — не сущности движка: любая модель — это Тело X. Колёса,
  подвеску, мотор и сцепление задаёт и считает проект; движок даёт только
  универсальные physics-расчёты.
- Каждая подсистема отключается CMake-опцией без поломки зависимостей.
- Качество графики задаётся одним пресетом `GraphicsQuality::Low|Medium|High`;
  любое поле `GraphicsConfig` перекрывается вручную.
- Целевое железо — Intel Iris Xe (iGPU): полная графика обязана держать высокую
  частоту кадров. Целевой уровень картинки — Forza Tech.
- Лицензия: полностью open source; конкретную OSI-лицензию утвердить до
  следующего публичного релиза.

## Ближайшие шаги

1. Закоммитить текущий рефакторинг dev-линии и синхронизировать её с
   `experimental/dev`.
2. Довести экспериментальные фичи до стабильного пути: материалы, MT-рендер,
   UI-слои, fog.
3. Физика: слои и маски коллизий, CCD, API телеметрии контактов.
4. Графика: PBR-текстуры, debug-draw коллайдеров/сил, CPU/GPU-профилирование,
   бюджеты iGPU.
5. UI: конструкторы меню и HUD поверх `UiDrawList` и текста.
6. Ассеты: кеш по папке, OBJ-импорт, handles по имени.
7. Расширенные модули: аудио, скрипты, сеть, softbody, skeletal-анимация.
8. Релизная гигиена: воспроизводимая сборка, CI, документация API.

## Критерии качества

- Сборка воспроизводима на чистой машине.
- У каждого этапа есть минимальный рабочий пример.
- Минимальная конфигурация не содержит отключённых модулей и лишних зависимостей.
- Ошибки диагностируются с контекстом, а не приводят к тихому падению.
- Производительность измеряется профилировщиком и бюджетами кадра.
- Физика детерминирована в пределах конфигурации и версии solver.
- Форматы ресурсов и состояние сцены версионируются.
- Критическая логика покрыта unit- и headless-тестами.
- Документация описывает архитектуру, CMake-опции, публичный API и решения.

## Открытые решения
