## Видение

Aporia Engine — большой модульный C++ игровой движок, подключаемый к игровому проекту как код. Это не редактор и не визуальный конструктор: игра сама создаёт сцену через публичный API, а движок выполняет динамическую симуляцию и предоставляет графический слой.

Первый приоритет — Windows x64, C++20 и headless CLI-тесты. Основной графический путь — Vulkan; окно, SDL3/GLFW и цикл приложения принадлежат внешнему игровому проекту. Внутри Aporia нет деления на «2D» и «3D»: сцена — это данные и симуляция, а графический backend можно подключить или отключить независимо.

Главная цель первого цикла — создать рабочую вертикальную срезу без редактора: внешний host → `Game` и сцена через API → фиксированная физическая симуляция → телеметрия нагрузок → подключаемый Vulkan-вывод. Сначала доказывается корректная динамика, затем добавляется визуальный слой.

## Главный критерий — скорость создания базы

Ключевая ценность движка — время от пустого проекта до работающей базы: окно юзера открыто, мир из мешей собран, Тело двигается вводом. Возможности движка оцениваются по вкладу в эту скорость, а не по количеству функций.

Модель, зафиксированная 2026-09-27:

- Юзер сам создаёт окно на любом API (Win32, SDL, что угодно) и сам держит цикл. Движок принимает дескриптор окна в Init-состоянии и от него инициализирует рендер — Vulkan по умолчанию. Движок никогда не создаёт окно сам.
- Сцена собирается через строителя (`SceneBuild`): юзер задаёт 2D или 3D и наполняет мир мешами, которые даёт движок. Сцена — контейнер данных; «мир» = меши внутри сцены.
- Центральная абстракция — Тело: трансформ + опциональная физика + опциональный меш. Персонаж, машина, снаряд — это Тело плюс код игры. Готовых сущностей («спавн персонажа», «спавн машины») в движке нет.
- Движок управляет input, render и закулисьем (время, физика, кеш ресурсов, память). Правила игры пишет юзер, связывая части движка между собой: нажал W → прикладал силу телу.
- Ассеты «просто работают»: пачку файлов скушивает кеш, выдача по имени; собственные форматы (модели из Omsi и т.п.) — код юзера поверх точек расширения.
- Счётчик успеха каждого этапа — строки хост-кода и минуты до работающей базы.

### Пересмотренный порядок этапов (2026-09-27)

Порядок реализации ниже перекраивает «План работ»: старые этапы остаются каталогом модулей, порядок теперь такой.

- Этап A. Init, SceneBuild и Тело: `InitState` (окно юзера → Vulkan-рендер), строитель сцены с режимом 2D/3D, Тело (меш + физика + автосинхронизация меша за телом), input движка (клавиатура/мышь), примитивные меши (box, sphere, plane, capsule) и камеры: орто для 2D, перспектива для 3D. Внутри движка: вершинные/индексные буферы, текстурированный меш. Цель: окно юзера + Init + сцена с Телом, движимым нажатием клавиш, ≤ 25 строк хоста.
- Этап B. Террейн: генерация ландшафта из heightmap/шума — меши мира + heightmap-коллайдер физики. Цель: холмистый мир, по которому ходит Тело, без единого файла ассетов.
- Этап C. Качество графики (2026-09-29): абстрактные пресеты качества Low/Medium/High, HDR-рендер, плавные PCF-тени, планарные отражения, автоматическое сжатие текстур. Цель: картинка масштабируется одним полем `GraphicsConfig::quality`, рефлект-сцена + HDR + тени показаны в отдельных render-тестах, память и скорость доказаны оптимизационным прогоном в CTest.
- Этап D. Физика второго уровня: контактные манифолды, итеративный solver, raycast. Нужен и ходьбе по склонам, и расчётным API транспорта (который собирает проект).
- Этап «UI и текст» реализован (2026-10-04): SDF rounded rects и Kawase/Gaussian blur (`UiDrawList`), TTF/MSDF текст (`TextRenderer` + `FontAtlasBuilder`), публичные `createFontFromTtf`/`createFontFromMsdf`, `setUiDrawList`, `setVsync`; персистентный текст-батч; тесты `AporiaTextTest`/`AporiaTextGuiTest` и render test 8. Остаются высокоуровневые конструкторы Pause Menu / Main Menu / HUD.
- Этап E. Физические расчётные API (без сущностей): движок не знает «машин» и «транспорта». Машина, слон, снаряд — это одно и то же Тело X (масса, прижимная сила, включаемость). Скорость, колёса, подвеска и мотор определяет и считает хост/проект; движок даёт только вызываемые расчёты (raycast, контакт/нормальная нагрузка, пружинно-демпферная подвеска и трение как функции от значений хоста) поверх универсального rigid body.
- Дальше прежний каталог: asset-кеш (папка текстур → кеш → handle по имени), OBJ-загрузка и свои импортёры, аудио, скрипты, сеть.

## Принципы разработки

- Сначала вертикальная среза, затем расширение подсистем.
- Минимальные зависимости между модулями; границы задаются интерфейсами.
- Каждая возможность включается отдельной CMake-опцией.
- Минимальная сборка `core + tests` не должна зависеть от рендера, Vulkan, аудио или сети.
- Физический runtime должен работать без окна и графического драйвера.
- Aporia не владеет окном и не выбирает SDL3/GLFW; внешний host передаёт нужный graphics context или вызывает render API.
- Внутри движка нет обязательного деления на 2D/3D-модули; это может сделать внешний renderer или профиль проекта.
- Физика по умолчанию работает с фиксированным timestep около 300 Hz; публичный API позволяет изменить частоту и режим stepping.
- Платформенный код изолировать от игровой логики.
- Любую крупную подсистему проектировать вокруг тестируемого ядра.
- Не добавлять функциональность без измеримой цели этапа.
- Сохранять совместимость форматов ресурсов и версий сцен.
- Решения, которые трудно откатить, фиксировать в плане и ADR-документах.

Редактор не входит в состав проекта. Интеграция выполняется через CMake и публичные заголовки; игровой проект подключает движок как подкаталог и получает готовую shared library. Внешний host владеет окном, SDL3/GLFW, swapchain и своим циклом приложения.

## План работ

### Этап 0. Зафиксированные решения

- Язык runtime и тестов: C++20.
- Первая платформа: Windows x64.
- Публичный namespace: `Aporia`; внутренний namespace: `apr`.
- Компоненты сцены: runtime-типы с регистрацией по type id.
- Графика: Vulkan; Aporia отвечает за инициализацию renderer и графические ресурсы.
- Окно и SDL3/GLFW: принадлежат внешнему игровому проекту; Aporia получает нужный native/window/surface context.
- Редактор: не планируется.
- Способ подключения игры: `add_subdirectory` в CMake; Aporia остаётся обычной C++-библиотекой.
- Публичная модель: объект `Game`, владеющий renderer-фасадом; сцена доступна через `game.scene()`.
- Создание объекта возвращает стабильный handle; иерархия parent/child откладывается.
- Внутри Aporia нет обязательного деления на 2D и 3D.
- Физика: собственная универсальная реализация без готового physics engine.
- Первый collider-набор: sphere, box, capsule и convex hull.
- Solver: sequential impulses; `step()` без аргументов использует 300 Hz, пользовательский frame delta передаётся явно.
- `step(frameDelta)` использует accumulator и выполняет нужное число fixed substeps.
- Инициализация renderer выполняется явно через универсальный graphics context после создания окна host-проектом.
- Единицы физики: SI — метры, килограммы, секунды и ньютон.
- Координаты физики: Z-up; преобразование в Vulkan выполняется на границе graphics API.
- Собственный минимальный test runner без обязательной внешней зависимости.
- Core, math, physics и tests используют только стандартную библиотеку C++20; Vulkan подключается только в graphics-модуле.
- Транспорт/машины — не сущности движка: любая модель (машина, слон, снаряд) — это Тело X. Колесо-raycast, подвеску, мотор и сцепление задаёт и считает проект; движок предоставляет только универсальные physics-расчёты как API.
- Первые проверки: CLI, unit-тесты и headless physics-тесты.
- Пятый физический тест: столкновения, отскок, трение и проникновение тел.
- Проект игры не получает отдельный формат manifest на первом этапе: всё подключается через CMake и вызовы C++ API.
- Библиотека по умолчанию собирается как shared DLL с именем `AporiaEngine.dll` и копируется рядом с EXE host-проекта.
- Лицензия: полностью open source; конкретную OSI-лицензию утвердить до первого публичного релиза.
- Требование к сборке: каждая подсистема отключается CMake-опцией без поломки зависимостей.
- (2026-09-27) InitState: движок принимает HWND окна юзера, размер вычисляет сам из клиентской области; цикл сообщений остаётся у юзера.
- (2026-09-27) Тело = стандартные компоненты сцены (Transform, MeshRef, PhysicsRef) и convenience `Game::createBody(BodyDesc)`; синхронизация Transform за физическим телом — обязанность движка в конце `step()`.
- (2026-09-27) 2D/3D: сцена единая; режим задаёт только камеру по умолчанию (орто против перспективы), отдельного 2D-пайплайна нет.
- (2026-09-27) Input: опросная модель с подключаемым источником состояний (Win32 по умолчанию, инжекция для тестов); CMake-опция `APORIA_ENABLE_INPUT`.
- (2026-09-29) Качество графики задаётся одним пресетом `GraphicsQuality::Low|Medium|High`, а не набором флагов. Низ — простое освещение без HDR и отражений, тени минимальные, текстуры сжаты пополам. Средний — добавляются HDR-таргет с ACES-тонмаппингом, PCF-тени 3×3 и полусайзовые планарные отражения, текстуры на 3/4. Высокий — тени максимального размера 5×5 PCF, полноразмерные отражения, текстуры нативные без урезания.
- (2026-09-30) Целевое железо — Intel Iris Xe (iGPU): террейн и полная графика (HDR, тени, отражения) обязаны выдавать высокую частоту кадров на нём. Каждая графическая фича проектируется с учётом бюджета iGPU.
- (2026-09-30) Целевой уровень картинки — Forza Tech: HDR, мягкие тени, отражения, чистый тонмаппинг как база, дальше наращиваем.
- (2026-09-30) Вся графика настраиваемая от A до Я через `GraphicsConfig` программно: масштаб рендера, сжатие текстур, сила LOD, дальность прорисовки, FPS-ограничение, качество/размер теней, режим отражений, тонмаппинг и т.д. Пресеты Low/Medium/High лишь заполняют этот конфиг, но любое поле перекрывается вручную.

### Этап 1. Фундамент репозитория и сборки

- Настроить структуру каталогов и namespaces.
- Выбрать стандарт C++, CMake presets и основной генератор сборки.
- Добавить форматирование, статический анализ, sanitizers и тестовый runner.
- Реализовать логирование, конфигурацию, ошибки и assertions.
- Добавить публичные include-каталоги, export/import настройки и target `AporiaEngine` с output name `AporiaEngine.dll`.
- Добавить post-build копирование DLL в каталог EXE host-проекта при подключении через CMake.
- Реализовать матрицу конфигураций: `core-only`, `physics`, `graphics`, `softbody`, `audio`, `networking`, `tests`. Отдельного `vehicle`-модуля нет: транспорт — это Тело X и код проекта.

**Результат:** движок собирается в нескольких конфигурациях, включая минимальную headless-сборку без графики.

### Этап 2. Headless core и API сцены

- Публичный API жизненного цикла `Game` и сцены без окна.
- Renderer-фасад входит в `Game`, но окно и его backend остаются во внешнем host-проекте.
- Явный `initGraphics(context)` принимает универсальный контекст окна/платформы.
- Создание объектов возвращает стабильные handles; иерархия parent/child не входит в первый API.
- Единицы измерения и координатные преобразования проверяются на границах API.
- Фиксированный timestep по умолчанию 300 Hz; `step()` использует стандартный шаг, `step(frameDelta)` — переданное значение через accumulator.
- Публичное изменение частоты, максимального числа substeps и поведения при перегрузке.
- Часы, конфигурация, обработка ошибок и детерминированный порядок систем.
- Математические типы: векторы, матрицы, кватернионы, AABB, sphere и ray.
- Сериализация состояния сцены и настроек.
- Минимальный CLI: загрузка конфигурации, запуск сцены, вывод телеметрии и корректное завершение.

**Результат:** игра создаёт сцену через `game.scene()` и выполняет детерминированный цикл симуляции из консоли без редактора и окна.

### Этап 3. Физическое ядро

- Собственный broad phase, narrow phase, solver и dispatcher.
- Общие rigid body API: масса, инерция, силы, импульсы, трение и ограничения.
- Набор универсальных collider-примитивов и материалов поверхностей.
- Gravity, столкновения, контактные точки, трение и восстановление.
- Слои collision filtering, sleeping и continuous collision detection.
- Модель solver должна быть расширяемой и не зависеть от игровых сущностей или рендера.
- Профилирование физики: broad phase, solver, broad/narrow phase, sleep и память.

**Результат:** физика работает без рендера, имеет фиксированный timestep и покрыта воспроизводимыми тестами.

### Этап 4. Физические расчётные API (не сущности)

- В движке нет типов Vehicle/Car/Wheel/Suspension/Engine как игровых сущностей.
- Единственный строительный блок — Тело: трансформ + масса + прижимная сила + включаемость (enabled/sleep); давление и нагрузка выводятся из контактов, а не хранятся движком как «машина».
- Движок даёт проекту вызываемые расчёты: raycast колеса, пружинно-демпферная подвеска как функция от заданных хостом значений (жёсткость, ход, точка крепления, точка контакта), трение/сцепление как функция нормальной нагрузки, момент и сила от приложенной точки.
- Состояние (скорость, крутящий момент, передача, рулевой угол) хранит и интерпретирует проект; движок только считает переданные значения и возвращает результат.
- Телеметрию (нагрузки, проскальзывание, перегрев и т.д.) проект собирает из API (контакты, силы, raycast) и экспортирует сам.

**Результат:** проект собирает машину или персонажа из Тела X и вызовов расчётных API, без единого engine-типа про транспорт.

### Этап 5. Ресурсы и сцены из кода

**Результат:** проект из папки можно запустить без ручного редактирования внутренних файлов движка.

### Этап 6. Графический слой и Vulkan

Текущий срез: headless offscreen pipeline, Win32 native swapchain и 2D texture resources проходят smoke, resize и длительный stress test. Camera, geometry/material resources и presentation synchronization пока не реализованы.

- Общий graphics interface без обязательного деления на 2D/3D.
- Aporia инициализирует Vulkan device, swapchain, queues и render passes через универсальный graphics context.
- Внешний host создаёт окно через SDL3/GLFW/другой backend и передаёт Aporia callbacks или opaque platform data.
- Камера, геометрия, шейдеры, текстуры, освещение и ресурсы сцены.
- Физика и graphics не зависят друг от друга; renderer можно отключить полностью.
- Визуализация debug-данных: коллайдеры, векторы сил, контакты, нагрузки и траектории.
- Профилирование GPU и CPU.

**Результат:** один и тот же runtime может быть запущен headless через CLI или подключён к окну внешнего host-проекта с инициализированным Aporia Vulkan renderer.

## Первые измеримые milestones

### Milestone A. Headless physics

CLI-тесты должны доказать, что движок считает универсальную динамику тел и расчётные API, а не только перемещает объекты:

1. Движение и поворот тела под силами/импульсами и моментом (без понятия «автомобиль»).
2. Тело на склоне-террейне: нормальная нагрузка и контактные силы выводятся из контактов.
3. Падение и приземление: зависимость от массы и пиковые нагрузки.
4. Тяжёлое тело массой около двух тонн на статическом теле: распределение нагрузки и просадка контакта.
5. Столкновения: проверка контакта, отскока, трения, импульса и отсутствия проникновения.
6. Расчётные API: колесо-raycast возвращает точку/нормаль/дистанцию, подвеска и трение считаются как функции от значений хоста.

Каждый тест запускается без окна, использует фиксированный timestep и сохраняет телеметрию. Проверки должны иметь численные допуски, а не только визуально считаться успешными.

### Milestone B. API и лёгкая сборка

- Игровой проект подключает Aporia через `add_subdirectory` как обычную C++-библиотеку.
- Сцена создаётся из пользовательского C++-кода через публичный API; отдельный manifest не нужен.
- Конфигурация `APORIA_ENABLE_*` собирает только нужные модули.
- Сборка `core + physics + tests` не требует Vulkan, окна или аудио.
- Smoke-тест подтверждает подключение библиотеки из папки проекта.

### Milestone C. Vulkan и внешний host

- Vulkan backend без владения окном.
- Камера, геометрия, материалы, текстуры и базовое освещение.
- Визуализация физических коллайдеров, сил, контактов/нагрузок и телеметрии.
- Внешний проект создаёт окно через SDL3, GLFW или другой backend и подключает Aporia в свой цикл.
- Переключение между headless CLI и визуальным запуском без изменения игровой логики.

## Критерии качества

- Сборка воспроизводима на чистой машине.
- У каждого этапа есть минимальный рабочий пример.
- Минимальная конфигурация действительно не содержит отключённых модулей и лишних зависимостей.
- Ошибки диагностируются с контекстом, а не приводят к тихому падению.
- Производительность измеряется профилировщиком и бюджетами кадра.
- Физика детерминирована в пределах заданной конфигурации и версии solver.
- Форматы ресурсов и состояние сцены версионируются.
- Критическая логика покрыта unit-тестами и headless physics-тестами.
- Документация описывает архитектуру, CMake-опции, публичный API и принятые решения.
